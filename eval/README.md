# 评测：模型会不会用这些工具

`tests/` 证明工具写对了，这里证明模型会用。两件事必须分开测——混在一起时，
模型答错你无法判断是工具描述有歧义，还是模型本身不行。

## 为什么不用现成的 agent 评测框架

试过的方案都不合适，理由是具体的：

| 方案 | 不用的原因 |
|---|---|
| RAGAS / 通用 LLM 评测 | 衡量的是文字质量，不看工具调用序列，而这里要测的恰好是"调了哪个工具" |
| 纯 LLM-as-judge | 每次跑分数都在漂，无法复现；而且判官本身也会幻觉 |
| 只测最终答案 | 答案对但过程错（比如只看了一张图就下结论）会被判为通过 |

所以判定全部基于**轨迹的机器可检事实**：调用了哪些工具、参数是什么、
回答里的数字能否在任何一次观测里找到。没有一处依赖另一个 LLM 打分。

## 五层判定

一条任务必须五层全过才算通过。少任何一层都会出现"看起来答对了"的假阳性：

| 层 | 字段 | 抓什么问题 |
|---|---|---|
| 工具 | `need` / `forbid` | 该调 `count` 却调了 `detect`；判断模糊度却跑了检测 |
| 轮次 | `min_calls` / `max_calls` | 简单问题绕 5 轮；两张图只处理一张 |
| 参数 | `arg_checks` | conf 没真降下去；`detail` 没设 full 却声称给了全部坐标 |
| 答案 | `match` / `not_match` / 数字溯源 | 断言"没得病"；给出每亩株数；数字在观测里找不到 |
| 覆盖 | `paths` | 多图任务只处理了一张就下结论 |

**轮次按"决策轮"算，不是按工具调用次数。** 模型可以在一轮里并行请求多个
工具（同时查两张图），这时调用次数会大于轮次。按次数算预算，会把并行
调用这种高效行为当成浪费步数罚掉。轨迹里每个 `Step` 都带 `turn` 字段。

**`arg_checks` 支持 `tool: "*"`**：任意工具的一次成功调用满足条件即可。
C1「把阈值降到 0.15 再数一遍」，用 `refine_detection` 还是再调一次
`count_cabbage` 都是对的——那是实现路径不同，不是做错。真正要约束的是
"conf 有没有真的降下去"。

`paths` 这条是刻意加的。C3 问"两张图哪张更密"，模型只检测第一张、拿它的
数字作答，前面四层全都会通过——只有比对参数里的真实路径才能发现。

## 幻觉率怎么算

不靠判官，靠溯源。规则：回答里每个数字都必须能被某次观测里的数字解释。

三个放宽条件，目的是不冤枉合理推理：

1. **0~3 的整数豁免**——"两张图""差 2 株"这类是结构用法，不是断言
2. **允许派生值**——任意两个观测数字的差、比值的百分数，覆盖"差 +1""降了 2%"
3. **容差**——绝对 0.005、相对 0.5%，处理浮点格式化

**问题里的数字也算来源。** 用户问"用 conf=1.5 检测"，回答复述 1.5 和工具的
合法区间 0.05~1.0 是正常的；只比对观测会把它判成编造。

剩下的就是无出处。这个措辞是刻意的：其中一部分是模型自己算出来的派生值
（如"46.7 株/兆像素"），计算过程可能合理但不可核验，与凭空捏造不是一回事。
指标定义：

```
幻觉率 = 含无法溯源数字的任务数 / 回答中含数字的任务数
```

分母排除"回答里一个数字都没有"的任务，否则拒答类任务会被算成满分。

## 三种"看起来该判失败、其实不该"的情况

写完第一版跑真实模型，抓到三处判定在冤枉模型，都已修：

| 现象 | 真相 | 改法 |
|---|---|---|
| 回答里 `0.805` 被判无出处 | 观测里就有 `0.805`，但去重时 `round(v,2)` 把它舍成 `0.81`，浮点差值恰好越过容差 | 只洗浮点噪声（6 位），不降到 2 位 |
| 越界 conf 任务判"没处理错误" | 模型主动把 1.5 收敛到上限 1.0 再跑，压根没触发错误——这是更好的行为 | 只要最后给出有效结论就算恢复，是否真触发错误单独统计 |
| 给出"若 GSD=1cm 则约 312 株/亩"被判违规 | 已明确标注"不是检测结果，只是公式代入" | 任务可声明 `exempt_if`，命中则不按禁语和无出处判 |

## 用法

```bash
# 自检：不需要 key，验证评测管线本身
python eval/run_eval.py --provider mock

# 真实模型
CVAGENT_EVAL_DATA=/path/to/test/images \
  python eval/run_eval.py --provider dashscope

# 只跑错误恢复那组，迭代 hint 文案时用
python eval/run_eval.py --provider dashscope --only recover
```

参数：`--only <分类>`、`--limit N`、`--max-steps`、`--device`、`--out-dir`。
结果写到 `eval_reports/eval_<provider>[_<分类>].{json,md}`。

## 数据与 fixture

真实图片不随仓库分发，`--data-root` 指向本地测试集（默认
`../cabbage_project/dataset/test/images`）。缺数据的任务标 **SKIP** 而不是判失败——
否则在没有数据集的环境里分数会虚假地变低。

错误恢复、不可用图这两组用的是**合成 fixture**（8×8 图、纯黑图、后缀撒谎的文本、
不存在的路径），所以这 9 条在任何机器上都能跑。

## 读分数时注意

`provider=mock` 的分数**不代表模型能力**。mock 是一个按预设脚本行动的替身
（检测 → 看 n_low → 复核 → 收束），它根本不读问题。跑它有两个用处：

1. 验证评测管线本身（能跑完、能算分、能出报告）
2. **反向验证判定没有过松**——如果 mock 在所有任务上都通过，说明约束写虚了

当前 mock 通过 42%，失败集中在工具选择（省时类、批量类）、参数（detail/conf）
和越界拒答——这三类恰好是 mock 的脚本策略无法覆盖的，符合预期。

对照：`qwen3.8-27b` 实测通过 96%、工具选择 100%、参数 100%、错误恢复 100%、
幻觉 0%。两条基线的差距就是这个评测的分辨力所在。

## 环境故障不算模型失败

额度耗尽、网络超时这类问题会记成 `status=error`，**不计入任何分母**，
在报告里单列"环境故障 N 条"。不这么分的话，一次 403 就能把 96% 压成 77%，
而真正的原因在账户余额，不在模型——那是最容易自己骗自己的一种数字。

代价是报告的头条数字只覆盖一部分任务，所以只要有环境故障，报告头部会多出一段
告警，列出**具体缺哪几条**。实测踩过一次：`--provider auto` 选中的默认模型没有
免费额度，6 条需要 Agent 的任务全被剔除，剩下的 23 条全是规则命中，报告于是写着
「通过率 100%、升级率 0%」——读起来像规则泛化得好，其实那一次一个模型都没调。
**只有环境故障 0 条的报告才能和全量报告横比。**
