# 确定性管线：为什么不是所有请求都该进循环

这份文档回答一个被反复问、但很少被量化的设计问题：

> 一个视觉问答应用，什么时候该把请求送进 LLM 循环，什么时候该用写死的流程？

答案不靠直觉，靠一组对照实验。同一条请求、同一批工具、同一套判据，只换决策方式。

---

## 0 结论

|  | 主任务集（26 条，规则参考过） | **留出集（8 条，规则没参考过）** | 零 LLM 占比 | 延迟中位 |
|---|---|---|---|---|
| 确定性管线 | 100% | **38%** | 100% | **0.13 s** |
| Agent（qwen3.8-27b） | 92% | **88%** | 0% | 11.64 s |
| **分层（今天跑的那条路）** | **100%** | **88%** | **85% / 38%** | 规则 0.14 s |

延迟差 **90 倍**，留出集准确率差 **50 个百分点**。

但第三行才是重点：**分层的通过率不低于纯 Agent，而 85% 的请求根本没用 LLM。**
它不是两者的折中，是一个下界不降、成本大降的组合。这件事已经落到代码里
（`ask --mode auto` 是默认值），不是一张规划表——见第 5 节。

所以边界不在"问题难不难"，而在**措辞能不能被枚举**：

- 请求来自固定入口（表单、API、固定的提示词模板）→ 措辞是可枚举的，pipeline 完胜。
- 请求来自自由文本（聊天、语音转写）→ 措辞不可枚举，必须上 Agent。
- 26 条上的 100% 是过拟合的证据，不是能力的证据。这一点下面第 6 节展开。

---

## 1 判断准则：先换一个问法

常见的判据是"答案是否依赖上下文（历史对话、多张图、领域知识）"。这条不准，两个方向都会错：

| 反例 | 依赖上下文？ | 需要 Agent？ | 为什么 |
|---|---|---|---|
| 带历史的客服问答 | 是 | **否** | 一次 RAG + 生成就结束，没有"看结果再决定下一步" |
| 「订明天去北京的机票」 | 否 | **是** | 查航班→比价→改签，每步结果决定下一步 |

真正决定的是另一件事：

> **能不能在写代码的时候，就把工具调用序列写死。**

能写死 → pipeline，哪怕要读历史、要查知识库。
写不死（下一步取决于上一步返回了什么）→ Agent。

领域知识同理：甘蓝的株距、密度分档、k=0.53 全是常量，写进配置就行，不构成 Agent 的理由。
"有领域知识"不是判据，"领域知识需要在运行时权衡"才是。

---

## 2 实现：三条刻意的选择

`src/cvagent/pipeline.py`，约 450 行，**零 LLM 调用**。

**1. 不猜。** 路由靠正则，命中就执行，不命中就明说"无法确定要执行哪个动作"。
猜错比不做更贵——用户会拿到一个看似正常的错答案，而且不会怀疑它。

**2. 不绕过工具层。** 所有调用都走 `ToolRegistry.dispatch`，参数校验、错误语义、
观测截断与 Agent 完全同一套。这样对比的才是**决策方式**，而不是实现质量。

**3. 答案里不写死数字。** 模板只拼接观测里出现的字段。这让幻觉率结构性为 0，
代价是答案不如模型写得自然。

一个细节：conf 越界（`conf=1.5`）时，管线把它夹到 1.0 再跑一次。这就是 F2 那条任务
要考的行为——模型靠"理解 schema"做到，规则代码靠"读 schema 的 maximum" 做到，
两者都没有真正"理解"，但都做对了。

## 3 对照实验

同一批工具、同一个 `run_eval.py`、同一套五层判定（工具/轮次/参数/答案/覆盖）。

### 3.1 主任务集

| 指标 | pipeline | Agent |
|---|---|---|
| 通过率 | 100% | 92% |
| 工具选择 | 100% | 100% |
| 参数正确 | 100% | 100% |
| 幻觉率 | 0% | 0% |
| 平均步数 | 1.31 | 1.88 |
| 墙钟中位 | 0.13 s | 11.64 s |

Agent 的两条失败（A4、F2）都是**轮次超预算**，不是答错：A4 要求"株数 + 框尺寸分布"，
它调了 detect → refine → detect 三次；F2 的 conf=1.5 它连试三次才收敛。

### 3.2 留出集（关键）

`eval/tasks_holdout.yaml` 的 8 条是**规则写完之后**才写的，意图与主任务集一一对应，
用词刻意偏离规则里出现过的说法。

| 任务 | 意图 | pipeline | Agent | pipeline 卡在哪 |
|---|---|---|---|---|
| H1 | 计数 | ✗ | ✓ | 「几**棵**」不是「几株」，「瞧瞧」不是「数」 |
| H2 | 密度 | ✓ | ✓ | — |
| H3 | 质量 | ✗ | ✗ | 「对**焦**跑**了**」不在词表 |
| H4 | 复核 | ✗ | ✓ | 「**门槛**压到 0.2」不是「阈值降到」 |
| H5 | 批量 | ✓ | ✓ | — |
| H6 | 批量前 N | ✗ | ✓ | 「**头** 5 张」不是「前 5 张」，量词一换抽取就落空 |
| H7 | 错误恢复 | ✗ | ✓ | 「**读**一下这个文件」里没有"检测/数/图" |
| H8 | 越界拒答 | ✓ | ✓ | — |

## 4 两种失败不在同一层

这是整个实验最值钱的发现。

**pipeline 死在语言层**：同义词（几棵/几株）、隐喻（对焦跑了 = 模糊）、量词（头/前）、
缺动作词（读文件 = 检测）。这四类都无法用加规则解决——加一条，换个说法又漏。

**Agent 死在决策层**：
- H3 它调了 `detect_cabbage`（任务明确 forbid）——想"顺手确认一下"，结果违反"判断模糊只需元信息"
- H2 多调了一次 `search_docs` 查密度口径，超出 2 轮预算
- A4、F2 绕路，超出轮次预算

也就是说：**pipeline 的错是"没听懂"，Agent 的错是"听懂了但走了弯路"。**
前者需要语言模型，后者需要更紧的提示或更宽的预算——两者不能互相替代。

一个细节值得记：同一句意思，B3（「是不是拍糊了」）Agent 做对了，H3（「对焦好像跑了」）
它做错了。**措辞变化会让 Agent 的决策也抖动**，只是抖得比正则轻。

## 5 分层已经落到代码里

不是二选一，是分层。这已经是 `ask` 的默认行为（`--mode auto`）：

```
请求 → Pipeline.route（正则，0 成本）
         ├─ 命中 → 确定性执行 → 直接交付（0 次 LLM，中位 0.14 s）
         └─ 未命中 / 可恢复错误 → 交接给 Agent 循环（N 次 LLM，中位 8.7 s）
```

升级判据只有两条，都能从 `Trajectory` 机械读出来，不读答案文本：

1. `stopped_reason == "pipeline_unrouted"` —— 措辞不在规则覆盖内
2. 某个 step 的 `error.retryable == true` —— 换个参数还能成，正是循环擅长的地方

**故意没实现的**：检出 0 株、置信度双峰、图质量分低于阈值。这些是业务判断，
升级率会失控，而且没有任何证据说明 Agent 在这几种情况下答得更好。要加，先有数据。

### 5.1 实测

| 任务集 | 规则命中 | 总通过 | 规则路径 | 升级路径 |
|---|---|---|---|---|
| 主任务集 26 | 22（**85%**） | 100% | 100% / 0.14 s | 100% / 14.6 s |
| 留出集 8 | 3（**38%**） | 88% | 100% / 0.11 s | 75% |
| 新增空间分布 3 | 0（**0%**） | 100%（`--provider auto`） | — | 100% |

两组的通过率都不低于纯 Agent（92% / 88%）。留出集那 12% 的失败是 H3，
纯 Agent 跑同一条也是同样的失败（连调用序列都一样），所以不是分层引入的回归。

第三行是补 `grid` 字段时新加的 S1–S3（分布均匀吗 / 最密最稀 / 缺苗率）。规则层
**一条都不接**：空间格局没有确定性动作，硬接只会像坑 3 那样答错粒度。所以纯
pipeline 在这三条上是 0%，`--provider auto` 升到 Agent 后 3/3 通过、幻觉 0%。
这也是分层该有的样子——不是"规则尽量多答"，是"答不了的别硬答"。

### 5.2 踩到的三个坑

**坑 1：宽规则不能顶替。** 留出集 H6「先跑头 5 张试试水」，`extract` 只认「前 N 张」，
抽不到 `limit`，于是路由落到更宽的 `batch_total`，把 75 张全跑了一遍，答案汇报
「合计 4134 株」。**它没报错**——这是最糟的失败形态：看起来正常、实际答非所问。

修法是在 `route` 开头拦一道，而不是在事后加判据：

```python
if _SUBSET_RE.search(question) and s.limit is None:
    return None      # 要子集但认不出张数，宁可交给 Agent，也不跑全量
```

**坑 2：空手交接会带乱节奏。** 路由未命中时 pipeline 一步没走，但 `handoff()` 仍拼了
一句「已尝试：无工具调用」。模型读到这句，像是被告知任务还没开始，H3 因此多跑一轮
（3 次调用，超出 2 次预算）。改成：

```python
if not pre.steps:
    return ""        # 空手升级就退化成纯 Agent，那才是它该有的样子
```

**坑 3：粒度不匹配也会越权。** 补 `grid` 字段那次联调，「最密的那一块有几株」
被 `count` 规则命中（`几株`），答成整图 62 株。数字对，问题错：用户问的是一格，
回答的是全图。同一类问题还有「分布得均匀吗」「哪块空着」——规则层没有对应动作，
它们本来就该升级。

修法同样在 `route` 开头，而不是给每条规则加后向断言：

```python
if _SPATIAL_RE.search(question) and not _NONSPATIAL_DIST_RE.search(question):
    return None      # 空间格局没有确定性动作，交给 Agent 读 grid
```

`_NONSPATIAL_DIST_RE` 是为了不误伤「框的尺寸分布」「置信度分布」——那是统计量，
属于 `detect_boxes`，不是空间格局。**宁可漏挡，不可误挡**：漏挡顶多升级一次，
误挡会把一条本来能 0.1s 答完的问题推给模型。

三个坑的共同点：**错都不在"规则写得不够多"，而在"规则越权"**——一个用宽规则代替
了不做，一个用空上下文代替了没有上下文，一个用粒度不匹配的规则硬答。
加规则治不了这类病。

### 5.3 补全量评测时撞到的坑：把参数错误"修"成空结果

跑 29 条全量时 F2（「用 conf=1.5 检测这张图」）在分层路径上挂了，而且挂得很隐蔽：
升级到 Agent 后**一个工具都没调**，直接回答「conf=1.0 下都检不出，可视为 0 株」。

往前追一层，根因在规则层的参数修复：

```python
clamped = 1.0 if conf > 1 else 0.05     # 旧写法
```

1.0 是 schema 的合法上界，但拿它当阈值**几乎必然返回 0 株**。于是流程变成：
夹到 1.0 → `NO_DETECTION`（可恢复错误）→ 升级 → 交接文本里写着「已尝试 conf=1.0
无结果」→ Agent 顺理成章地认为不必再试。**参数错误被伪装成了一个看起来正常的空结果。**

这不是模型笨，是交接文本给了它一个错误的"已完成"信号。修法两处：

```python
if conf > 1:
    return DEFAULT_CONF      # 退回默认阈值，不是夹到上界
```

```python
# 交接文本的尾句必须点明「上面的调用是记录，不是结论」
return f"[前置规则层] 已尝试：{done}。这一层没收尾，以上只是已执行过的调用记录，"
       "不是结论：需要换参数重试就自己重新调用工具，不要直接沿用上面的结果作答。"
```

再加一条约束：**改过参数必须在答案里写明**（`_conf_note`）。静默替换比报错更糟——
用户会以为「49 株」是 `conf=1.5` 的结果。

改完 F2 由规则层直接答出（0 次 LLM）：`（请求的 conf=1.5 超出工具的 0.05~1.0，
已改用 conf=0.25。）检出 49 株……`，分层全量回到 29/29。

这个坑和前三个不是一类：前三个是"规则越权"，这个是"规则把错误修成了正常值"。
共同点是**失败看起来都像成功**。

## 6 这套数字的局限（必须一起说）

1. **26 条上 pipeline 的 100% 是过拟合。** 规则是看着这 26 条的措辞写的，100% 是
   必然结果，不能当能力指标。真正的数字是留出集的 38%——分层之后同一批变成 88%，
   因为 62% 升级给了 Agent。
   补 `grid` 后任务集变成 29 条（多出的 S1–S3 规则层不接），纯 pipeline 因此显示
   90%（26/29）；**这 3 条的下滑是设计如此，不是回归**——原有 26 条仍是 26/26。
2. **留出集只有 8 条**，一条任务值 12.5 个百分点，无法给置信区间。"分层不低于纯 Agent"
   这个结论只在这 8 条上成立，样本太小，不能外推。
3. **两个延迟中位数不是同一批任务算的。** 纯 Agent 的 11.64 s 是 8 条全算，分层的
   8.72 s（留出集）/ 14.59 s（主任务集，仅 4 条）只算升级的那部分。样本不同，
   不能横比"升级比直接跑慢还是快"。
4. **Agent 的分数会漂。** 主任务集两次运行是 96% 和 92%（A4 稳定失败，F2 在两次之间变化），
   温度设为 0 也不保证云端逐字复现。所以 92% 是一次快照，不是区间。H3 也是同一种漂移：
   上一轮通过，这一轮两次都失败。
5. **延迟不含冷启动。** 评测里每条任务前会 `clear_cache()`，但权重已预热（约 28 s，
   不计入任务耗时）。0.14 s 是热进程内的单次检测，不是端到端首包延迟。
6. **判定又修了两处误伤**（详见第 7 节），说明"判据比模型更容易错"这件事在留出集上
   依然成立。

## 7 留出集上抓到的两个判定 bug

写判据时又犯了和主任务集同一类错误，记下来因为它有共性。

**H8 第一版**：`not_match: ["缺素"]`。模型答「我判断不了，没有针对缺素的诊断能力」，
因为出现了"缺素"两个字被判成编造。**禁语锚定了名词，而名词是问题本身带的。**

**H8 第二版**：改成 `not_match: ["没有缺素"]`。模型答「知识库里也没有缺素症相关的判定依据」，
子串"没有缺素"命中，又判错。**否定词 + 名词仍然不是断言。**

**第三版**：只锚定结论句式——`确实(是|有)缺素|确诊为缺素|植株(都)?健康|生长正常`。
通过。

三次修改的教训是一致的：**禁语要锚定"对事实下结论"的句式，不能锚定话题词。**
这与主任务集里那四处"冤枉模型"是同一类错误的第 5、6 次复发。

## 8 复现

```bash
# 确定性管线
python eval/run_eval.py --provider pipeline
python eval/run_eval.py --provider pipeline --tasks eval/tasks_holdout.yaml

# Agent 对照（需要 key）
python eval/run_eval.py --provider dashscope --model qwen3.8-27b
python eval/run_eval.py --provider dashscope --model qwen3.8-27b --tasks eval/tasks_holdout.yaml

# 分层（线上那条路）：规则优先，判断不了才升级
python eval/run_eval.py --provider auto --model qwen3.8-27b
python eval/run_eval.py --provider auto --model qwen3.8-27b --tasks eval/tasks_holdout.yaml

# 契约测试
python -m unittest discover -s tests -p "test_pipeline.py"
```

报告落在 `eval_reports/eval_{pipeline,dashscope,auto}[_tasks_holdout].{json,md}`，
任务集不同不会互相覆盖。`auto` 的报告会多一张「分层路由」表（规则/升级各多少条、
各自通过率与延迟），以及每条任务实际走的哪条路（`rows[].route`）。
