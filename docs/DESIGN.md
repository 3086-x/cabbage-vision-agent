# 设计说明

记录每个关键取舍的理由，以及**没有选的方案为什么不选**。面试时被追问"为什么这样设计"，
答案在这里，而不是临场编。

---

## 1 问题定义

给定一张无人机航拍甘蓝图，用自然语言回答三类问题：

- 有多少株？（计数）
- 长得密不密？（分级）
- 这个数字准不准？（不确定性）

难点不在检测——检测已有 0.970 的 mAP。难点在于：**模型给出的数字，凭什么信。**

所以项目的核心不是"接上 LLM"，而是让答案带上可追溯的依据：每个数字都能指回
某次工具调用、某个阈值、某次复核。

---

## 2 为什么是独立 Agent，不是 MCP 工具集

两条路都能体现"把模型能力抽象成接口"，差别在**能不能展示决策**。

MCP server 只暴露工具，决策发生在别人的客户端里。面试官问"这是 tool 还是 agent"，
选 MCP 路线只能回答"是 tool"。

独立 Agent 应用包含完整的循环：模型看到观测 → 判断数字不稳 → 自己决定复核 → 对比 →
给结论。这段决策链是"agent"两个字的唯一证据，也是这个仓库存在的理由。

代价是要自己写循环、上下文管理、错误传播。这三件事恰好是 Agent 工程的真问题，
所以代价本身也是收获。

---

## 3 分层与依赖方向

```
cli  →  agent  →  tools  →  vision
        ↓         ↓
       llm      errors
```

依赖只能向下，`vision` 不知道 LLM 存在。这样做的实际收益：

- 换模型不动业务代码（`llm/` 之外一行不改）
- 检测可以独立测试（`cvagent detect` 不经 LLM，出问题时能立刻分清是"模型不会用工具"
  还是"检测本身错了"）
- `vision` 可以被别的应用直接复用

`errors.py` 放在最底层，因为工具层需要它，而它不依赖任何东西。

---

## 4 工具粒度：为什么是 5 个

一个 `detect(image, conf)` 也能跑，但会让模型没有选择空间。5 个工具的划分依据是
**决策点而不是功能点**：

| 工具 | 对应决策 |
|---|---|
| `inspect_image` | 这张图值不值得花时间检测 |
| `detect_cabbage` | 要多少信息才够回答 |
| `count_cabbage` | 只要数字时，别浪费 token |
| `refine_detection` | 数字不稳，要不要复核 |
| `batch_detect` | 用户给的是文件夹还是单图 |

反面案例：把 `conf` 写死在代码里。那样模型永远无法"发现数字可疑并自救"，
`n_low` 也失去意义——它变成一个纯展示字段。

---

## 5 错误分类学

分类维度只有一个：**换个参数再试是否可能成功**（`retryable`）。

这个维度之所以有效，是因为它直接对应模型能采取的动作。`IMAGE_NOT_FOUND` 重试一百次
也没用，必须转告用户；`NO_DETECTION` 则是明确的"阈值太高"信号。

配套的 `hint` 是给模型看的建议，不是给人看的堆栈。写 hint 的原则是**给动作不给诊断**：
"把 conf 降到 0.10 重试" 优于 "置信度阈值过高可能导致召回不足"。

实现上的关键决定：`dispatch` 永不抛异常。任何未预期异常兜底成 `TOOL_CRASH`，
循环因此不会因为一个工具的 bug 而中断——在 Agent 场景里，能继续跑比快速失败更重要。

---

## 6 上下文预算

一张密集图 80 个框，全量序列化约 3000 token。跑 6 轮就吃掉整个上下文。

三层控制：

1. **默认视图只给统计 + 3 个框**（`summary`），全量要显式 `detail=full`
2. **单次观测字符上限**：默认 1400，检测全量放宽到 7000（因为那是模型显式要求的）
3. **历史压缩**：超过 6 条观测，把旧的换成一行摘要

第 3 点有个陷阱：不能删消息。`tool` 消息与 `assistant.tool_calls` 靠 `tool_call_id`
配对，删了会让多数供应商返回 400。所以只替换 `content`，保留结构——`test_loop.py`
里有一条测试专门守这个。

---

## 7 循环终止

三种终止：

| stopped_reason | 含义 |
|---|---|
| `stop` | 模型不再调工具，正常结束 |
| `max_steps` | 步数打满，已强制收束 |
| （异常） | provider 故障，CLI 返回码 2 |

`max_steps` 的处理不是直接 return。打满后发一次 **不带 tools** 的请求，逼模型用已有
观测作答，并把 `stopped_reason` 标记出来。理由：直接截断会得到半句话，而用户无法
区分"答完了"和"被掐断了"。

温度固定 0。这个任务没有创造性需求，需要的是可复现——同一张图问两次应当得到同一答案。

---

## 8 供应商抽象

只抽象三样：`Message`、`ToolCall`、`Completion`。任何 provider 只要能产出
`Completion` 就能接进循环。

协议差异收敛在 `openai_compat.py`：

- `function.arguments` 是**字符串**不是对象，且可能为空串或非法 JSON →
  解析责任交给工具层（`_parse_args` 容错），而不是在协议层假设它合法
- 429/5xx 标记可重试，401/400 直接失败
- 代理按 provider 单独配置，因为国内端点直连更强、境外端点必须代理，
  用全局环境变量会把两者一起带偏

已支持 DashScope / DeepSeek / OpenAI / Moonshot / 任意兼容网关（`custom`）。

## 9 评测计划（未完成）

当前只有契约测试，**没有量化"模型用得对不对"**。要补的是任务集：

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 工具选择正确率 | 该用 `count` 却用了 `detect_cabbage` 的比例 | 标注期望工具序列 |
| 参数正确率 | conf/detail 是否适配问题类型 | 同上 |
| 错误恢复率 | 注入 `NO_DETECTION` 后能自行降阈值的比例 | 构造失败场景 |
| 幻觉率 | 回答里的数字不在任何观测中的比例 | 自动比对轨迹 |
| 平均步数 | 完成任务所需工具调用数 | 轨迹统计 |

数据集：20~30 条问题，覆盖单图/批量/质疑/不可用图四类。这是下一步工作，
不是已完成项——README 的"局限"里已如实标注。

## 10 已知缺陷

- **`refine_detection` 依赖进程内缓存**。跨进程不可用，多用户部署时需要换成
  带过期的外部缓存（Redis 或按内容寻址的磁盘缓存）。
- **批量工具同步执行**。50 张图约 3 秒（GPU），可接受；上千张需要改并发 + 进度。
- **`inspect_image` 的边缘强度是近似值**。用相邻像素差代替拉普拉斯卷积，
  够用于"判断是否糊"，不能当清晰度指标做定量比较。
- **密度分级阈值来自训练集**。换场景（不同航高/品种）需要重新取分位数，
  当前硬编码在 `config.DENSITY_QUARTILES`。
