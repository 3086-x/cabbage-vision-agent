# 设计说明

记录每个关键取舍的理由，以及**没有选的方案为什么不选**。面试时被追问"为什么这样设计"，
答案在这里，而不是临场编。

---

## 1 问题定义

给定一张无人机航拍甘蓝图，用自然语言回答三类问题：

- 有多少株？（计数）
- 长得密不密？（分级）
- 这个数字准不准？（不确定性）

难点不在检测——检测已有 0.970 的 mAP。难点在于：**模型给出的数字，凭什么信。**

所以项目的核心不是"接上 LLM"，而是让答案带上可追溯的依据：每个数字都能指回
某次工具调用、某个阈值、某次复核。

---

## 2 为什么是独立 Agent，不是 MCP 工具集

两条路都能体现"把模型能力抽象成接口"，差别在**能不能展示决策**。

MCP server 只暴露工具，决策发生在别人的客户端里。面试官问"这是 tool 还是 agent"，
选 MCP 路线只能回答"是 tool"。

独立 Agent 应用包含完整的循环：模型看到观测 → 判断数字不稳 → 自己决定复核 → 对比 →
给结论。这段决策链是"agent"两个字的唯一证据，也是这个仓库存在的理由。

代价是要自己写循环、上下文管理、错误传播。这三件事恰好是 Agent 工程的真问题，
所以代价本身也是收获。

### 补记：这条理由的适用边界（2026-11-03 实测）

上面说的是"为什么选 Agent 而不是 MCP"，不是"为什么所有请求都该进循环"。后来用
确定性管线做了对照，结论是**大部分请求不该进**：

|  | 主任务集 26 条 | 留出集 8 条（换措辞） | 零 LLM 占比 |
|---|---|---|---|
| 确定性管线（0 次 LLM） | 100% | **38%** | 100% |
| Agent | 92% | **88%** | 0% |
| **分层（默认路径）** | **100%** | **88%** | 85% / 38% |

所以结构不是"全流程 Agent 化"，而是**规则路由兜主干、未命中才升级到循环**。
Agent 的正当性收窄到一件事：**措辞不可枚举的自由文本**。完整实验、失败模式对照
与复现命令见 [PIPELINE.md](PIPELINE.md)。

这条边界不是写在文档里就完了，它已经是 `ask` 的默认行为：`Pipeline.route` 命中就直接
交付（0 次 LLM），未命中或工具报可恢复错误才把控制权交给 `Agent`，并用 `handoff()`
把已做过的动作交代过去。`--mode` 可以把任一层单独拎出来跑，便于对照与排障。

这条边界反而让项目更站得住：能说清"我的 Agent 只在 15% 的流量上有必要"，
比声称"全流程 Agent 化"可信。

## 3 分层与依赖方向

```
cli  →  agent  →  tools  →  vision
        ↓         ↓
       llm      errors
```

依赖只能向下，`vision` 不知道 LLM 存在。这样做的实际收益：

- 换模型不动业务代码（`llm/` 之外一行不改）
- 检测可以独立测试（`cvagent detect` 不经 LLM，出问题时能立刻分清是"模型不会用工具"
  还是"检测本身错了"）
- `vision` 可以被别的应用直接复用

`errors.py` 放在最底层，因为工具层需要它，而它不依赖任何东西。

---

## 4 工具粒度：为什么是 6 个

一个 `detect(image, conf)` 也能跑，但会让模型没有选择空间。6 个工具的划分依据是
**决策点而不是功能点**：

| 工具 | 对应决策 |
|---|---|
| `inspect_image` | 这张图值不值得花时间检测 |
| `detect_cabbage` | 要多少信息才够回答 |
| `count_cabbage` | 只要数字时，别浪费 token |
| `refine_detection` | 数字不稳，要不要复核 |
| `batch_detect` | 用户给的是文件夹还是单图 |
| `search_docs` | 回答需要口径/依据时，去查文档还是凭印象说 |

反面案例：把 `conf` 写死在代码里。那样模型永远无法"发现数字可疑并自救"，
`n_low` 也失去意义——它变成一个纯展示字段。

---

## 5 错误分类学

分类维度只有一个：**换个参数再试是否可能成功**（`retryable`）。

这个维度之所以有效，是因为它直接对应模型能采取的动作。`IMAGE_NOT_FOUND` 重试一百次
也没用，必须转告用户；`NO_DETECTION` 则是明确的"阈值太高"信号。

配套的 `hint` 是给模型看的建议，不是给人看的堆栈。写 hint 的原则是**给动作不给诊断**：
"把 conf 降到 0.10 重试" 优于 "置信度阈值过高可能导致召回不足"。

实现上的关键决定：`dispatch` 永不抛异常。任何未预期异常兜底成 `TOOL_CRASH`，
循环因此不会因为一个工具的 bug 而中断——在 Agent 场景里，能继续跑比快速失败更重要。

## 6 上下文预算

一张密集图 80 个框，全量序列化约 3000 token。跑 6 轮就吃掉整个上下文。

三层控制：

1. **默认视图只给统计 + 3 个框**（`summary`），全量要显式 `detail=full`
2. **单次观测字符上限**：默认 1400，检测全量放宽到 7000（因为那是模型显式要求的）
3. **历史压缩**：超过 6 条观测，把旧的换成一行摘要

第 3 点有个陷阱：不能删消息。`tool` 消息与 `assistant.tool_calls` 靠 `tool_call_id`
配对，删了会让多数供应商返回 400。所以只替换 `content`，保留结构——`test_loop.py`
里有一条测试专门守这个。

## 7 循环终止

三种终止：

| stopped_reason | 含义 |
|---|---|
| `stop` | 模型不再调工具，正常结束 |
| `max_steps` | 步数打满，已强制收束 |
| （异常） | provider 故障，CLI 返回码 2 |

`max_steps` 的处理不是直接 return。打满后发一次 **不带 tools** 的请求，逼模型用已有
观测作答，并把 `stopped_reason` 标记出来。理由：直接截断会得到半句话，而用户无法
区分"答完了"和"被掐断了"。

温度固定 0。这个任务没有创造性需求，需要的是可复现——同一张图问两次应当得到同一答案。

## 8 供应商抽象

只抽象三样：`Message`、`ToolCall`、`Completion`。任何 provider 只要能产出
`Completion` 就能接进循环。

协议差异收敛在 `openai_compat.py`：

- `function.arguments` 是**字符串**不是对象，且可能为空串或非法 JSON →
  解析责任交给工具层（`_parse_args` 容错），而不是在协议层假设它合法
- 429/5xx 标记可重试，401/400 直接失败
- 代理按 provider 单独配置，因为国内端点直连更强、境外端点必须代理，
  用全局环境变量会把两者一起带偏

已支持 DashScope / DeepSeek / OpenAI / Moonshot / 任意兼容网关（`custom`）。

---

## 9 可观测性：为什么 token/耗时进轨迹

轨迹原本只有「调了什么工具、拿到什么」。这不足以回答三个运维问题：

- **贵在哪**：工具本身几乎不花 token，贵的是每轮把历史与工具 schema 再发一遍；
  所以 token 要按轮记，而不是只记总数。
- **慢在哪**：一次 `ask` 的 wall time 可能 90% 在等模型，也可能 90% 在推理；
  两者混在一个 `elapsed_ms` 里时，优化会拍脑袋。`llm_ms` 与 `tool_ms` 必须分列。
- **重试吃掉了多少**：限流发生在 provider 内部，外层只看到「这一轮特别慢」。
  `retries` 是唯一能把「慢」归因到限流的字段。

因此 `Trajectory.turns` 每轮记 `llm_ms / prompt_tokens / completion_tokens /
retries / tool_ms / n_calls`，`totals()` 汇总；报告里输出「## 开销」表。
没有 usage 的 provider（mock、部分流式网关）记 0，而不是估算——估算 token 会
让「省了多少」变成不可验证的叙事。

## 10 评测（已落地，已有真实分数）

契约测试只能证明工具写对了，"模型用得对不对"要靠任务集量化。这套东西已实现：
`eval/tasks.yaml`（26 条）+ `eval/run_eval.py`，指标定义见 `eval/README.md`。

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 工具选择正确率 | `need` 全部命中且 `forbid` 未命中 | 比对轨迹里的工具序列 |
| 参数正确率 | conf 降到位、`detail` 是否 full | 检查工具调用参数 |
| 错误恢复率 | 注入错误后仍给出有效答案 | 构造 4 类失败场景 |
| 幻觉率 | 回答里的数字无法在任何观测中找到 | 数字溯源 + 派生值白名单 |
| 平均步数 | 完成任务所需工具调用数 | 轨迹统计 |

判定分五层（工具/步数/参数/答案/覆盖），全部基于轨迹的机器可检事实，
不用 LLM-as-judge——判官本身会漂移，而且判官也会幻觉。

**真实模型实测（qwen3.8-27b，26 条全跑）**：通过 96%、工具选择 100%、
参数 100%、错误恢复 100%、幻觉 0%、平均 1.85 轮。唯一失败是 A4 多绕一轮。

mock 基线 42%，不能当模型能力看——它是按脚本行动的替身，跑它只为反向验证
判定没有过松。

### 判定里踩过的四个坑

写完第一版跑真模型，四处判定在冤枉模型，都已修并加测试：

1. **去重把精度丢了**：`round(v, 2)` 把观测里的 `0.805` 舍成 `0.81`，
   差值在浮点下等于 `0.0050000000000000044`，恰好越过 0.005 容差。
   等于先改坏观测再判它对不上。
2. **问题里的数字不算来源**：用户说"用 conf=1.5 检测"，回答复述 1.5 被判编造。
   而且一开始传的是带 `{single}` 占位符的原始问题，路径里的 `img_106` 也没被认。
3. **把"避免错误"当成"没处理错误"**：模型主动把越界 conf 收敛到上限再跑，
   压根没触发错误，却被判失败。现在只要最后给出有效结论就算恢复。
4. **按调用次数算步数预算**：模型一轮并行调两个工具（同时查两张图），
   被当成浪费了两步。现在 `max_calls` 按轮次、`min_calls` 按调用数。

第 4 条是典型的"指标比模型更笨"：不区分"并行"和"绕路"，就会惩罚正确行为。

### 顺带抓出来的两个真问题

写评测时发现的两个缺陷，都已修复并加了回归测试：

1. **缓存阈值穿透**：跑过 `conf=0.15` 之后再调 `conf=0.25`，命中缓存后直接返回
   了 0.15 的结果，阈值参数被静默忽略——株数 49 变成 50。工具"看起来正常"，
   数字却是错的。修复方式：命中缓存时按本次阈值过滤框，不重新推理。
   `tests/test_engine.py::TestCacheThresholdSemantics` 四条测试锁住这个语义。
2. **评测间的状态泄漏**：26 条任务共用同一个 engine，上一条的缓存污染下一条，
   导致 `before.conf` 取到 0.15。修复方式：每条任务前 `clear_cache()`。

第一个问题是这个评测真正的价值——**不做任务集就发现不了**，因为单条调用路径
永远是对的，只有"先低阈值复核、再问默认阈值"这个序列才会暴露。

## 11 已知缺陷

- **`refine_detection` 依赖进程内缓存**。跨进程不可用，多用户部署时需要换成
  带过期的外部缓存（Redis 或按内容寻址的磁盘缓存）。
- **批量工具同步执行**。50 张图约 3 秒（GPU），可接受；上千张需要改并发 + 进度。
- **`inspect_image` 的边缘强度是近似值**。用相邻像素差代替拉普拉斯卷积，
  够用于"判断是否糊"，不能当清晰度指标做定量比较。
- **密度分级阈值来自训练集**。换场景（不同航高/品种）需要重新取分位数，
  当前硬编码在 `config.DENSITY_QUARTILES`。
